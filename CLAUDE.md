# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A framework for driving robots from human electrophysiological signals (EEG/EMG). The pipeline is fixed: a `signal` source is decoded by a `decoder` into a raw prediction, which a `command` translates into per-part actions sent to a `robot`'s `arm`/`hand`/`camera`. A decoder whose output is language-typed (`FeatureType.LANGUAGE`) is meant to route somewhere else entirely instead of through `command` — no such routing is implemented yet (`N2O.run()` just raises `NotImplementedError` for it currently; see the Architecture section below and `ROADMAP.md`). See [examples/README.md](examples/README.md) for the intended usage shape.

The only top-level project folders are `apps/`, `demos/`, `docs/`, `examples/`, `src/n2o/`, `tests/`, and `third_party/`. Anything else at the repo root (e.g. `notes/`, `sandbox/`) is local scratch/build output, gitignored, and not part of the tracked project structure. `ROADMAP.md` (a file, not a folder) at the repo root lists not-yet-implemented features (config checker, IK calculator, HW calibration, DOF check).

`docs/` is a bilingual (en/ko, `mkdocs-static-i18n`, `docs_structure: suffix` — an `index.md`/`index.ko.md` pair per page) MkDocs Material site (`mkdocs.yml` at the repo root, `docs` dependency group, deployed to GitHub Pages by `.github/workflows/docs.yml` on push to `main`) — usage documentation for how the pipeline's pieces fit together and how to extend them, one page per `src/n2o/` section (`architecture`, `signal`, `decoder`, `command`, `robot/arm`, `robot/hand`, `robot/camera`, `controller`, `third-party`) plus `getting-started/` and `tutorials/`. This is a *different* thing from `examples/`'s numbered notebooks (see below) — `docs/` explains concepts and how components connect, `examples/` is runnable step-by-step tutorial code; a `docs/` page cross-links to the matching notebook where one exists rather than duplicating its content. Serve locally with `uv sync --group docs && uv run mkdocs serve`; `uv run mkdocs build --strict` (what CI runs) fails on any broken internal link or unresolved heading anchor, so re-run it after touching cross-page links.

`third_party/` holds vendored copies of upstream projects that aren't installable Python packages (no root `pyproject.toml`/`setup.py`), so they can't be added as a normal `uv`/pip dependency — each vendored project gets its own subfolder plus a `NOTICE.md` documenting provenance (upstream repo/commit, what was copied, license), following the same provenance-doc convention as `src/n2o/robot/arm/so101/NOTICE.md`/`src/n2o/robot/hand/amazing_hand_right/NOTICE.md`. `third_party/AmazingHand/` (`Demo/`, `PythonExample/`, `LICENSE`, `README.md`, pinned to upstream tag `v1.0`) is the current occupant — see its own `NOTICE.md`; `src/n2o/robot/hand/amazing_hand_right/`'s `AmazingHand.move()` was ported from its `PythonExample/AmazingHand_Demo.py`.

## Architecture

`src/n2o/` mirrors the pipeline as sibling packages, most following the same extension pattern — a `base.py` ABC plus one file per concrete implementation, re-exported from that package's `__init__.py`. `signal/dataset/` and `signal/stream/` are one exception: their interface class lives in `loader.py`, not `base.py` (`DatasetLoader`/`StreamLoader` — see below). `decoder/` is another: `base.py`/`config.py` (the shared `Decoder` ABC and `DecoderConfig`/`DecoderType`/`FeatureType`) stay at `decoder/`'s top level, but `classification/`, `regression/`, and `utils/` are real subpackages underneath it — see below.

- `signal/dataset/` — offline/indexed signal sources. `DatasetLoader` is a concrete class (not an ABC), constructed with exactly one of `path` (a local folder) or `name` (a registered dataset library, e.g. `"Ofner2017"` — see `DatasetLoader.list_libraries()`). `DatasetLoader.info()` (an instance method, mirroring `read()`'s own `name`/`path` dispatch) returns a `DatasetInfo` describing the dataset's origin, cue-relative data range, and channel count. `DatasetLoader.library_tree()` renders the registry grouped by source (e.g. `"moabb"`); past `inline_limit` (default 30 — moabb alone registers ~150) it refuses to return the tree inline unless `to_file=` names a path to write it to instead.

    `DATASET_LIBRARY` is populated almost entirely by `moabb_entry.py`'s `MoabbLibraryEntry` — one dynamic subclass per class in `moabb.datasets.utils.dataset_list`, generated at import time rather than hand-written per dataset (moabb already carries `METADATA`/`interval`/`event_id` on each of its own dataset classes; `MoabbLibraryEntry.info()` reshapes that into `DatasetInfo` instead of duplicating it by hand). `moabb`/`braindecode` are core `n2o` dependencies for this reason (see below), not examples-only. A hand-written `DatasetLibraryEntry` subclass (the old per-file pattern, e.g. the removed `ofner2017.py`) is still the right call for a dataset moabb doesn't cover.

    Unlike every other `read()` in `src/n2o/` (still `NotImplementedError` stubs — see below), `MoabbLibraryEntry.read()` is for-real implemented — but only loads: it fetches subject 1's raw recording via `braindecode.datasets.MOABBDataset` and returns it as-is, nothing more. Preprocessing and windowing used to run here too but now live in `n2o.decoder` (see below) — turning a raw recording into decoder-ready windows is the decoder's job, not the signal source's, so `signal.read()` stays a plain loader. There is no train/valid-split helper anywhere — this project's example notebooks don't train a decoder, so one was never added.

    `path=` mode has no registry entry to source `DatasetInfo`/`read()` from, so it requires a `dataset_info.py` file to already exist inside `path` — `DatasetLoader(path=...)` itself raises `FileNotFoundError` at construction if it doesn't (`info()` never gets a chance to fail lazily). There's no constructor option to generate one: call `n2o.signal.dataset.write_metadata_template(path)` first (writes a blank, hand-fillable `DatasetInfo(...)` template; refuses to overwrite one that already exists), fill it in, *then* construct `DatasetLoader(path=...)`. `read()` stays a `NotImplementedError` stub regardless.

- `signal/stream/` — realtime/device signal sources. `StreamLoader` (`loader.py`) is the only class here — a sibling to `signal/dataset/`'s `DatasetLoader` rather than a subclass of it (mirrors `mne.io.Raw` vs `mne_lsl.stream.StreamLSL`). No concrete stream yet — same reasoning as `signal/dataset/` dropping `EEG`/`InvasiveEEG`/`EMG`: an interface-only stub subclass adds nothing over the ABC itself until a real device integration exists
- `decoder/` — signal → raw prediction decoders. `Decoder` (`base.py`) declares `decode()`, `preprocess()`, and `window()` as abstractmethods, plus a concrete `prepare(raw_dataset)` template method: `self.preprocess(raw_dataset, **self.config.preprocessing_kwargs)` then `return self.window(raw_dataset, **self.config.windowing_kwargs)`, using this decoder's own `config` (a `DecoderConfig`, set once at construction via `Decoder.__init__(self, config)` instead of a caller re-deriving and re-typing the right numbers by hand wherever the decoder gets used). `DecoderConfig` (`config.py`) carries `type`/`input_feature`/`output_feature` plus `n_times`/`windowing_kwargs`/`preprocessing_kwargs`/`labels` — one struct instead of a decoder holding a second, separate copy of the same facts. `prepare()` raises if `config.windowing_kwargs` was never set — there's no dataset-agnostic default for it. `labels` is the class-index-ordered label list a `Classification` decoder's own `window()` fills in automatically (via `label_names()`) once it has windowed data to read the mapping off of; `Command.translate()` can then read `decoder.config.labels[decoded_signal]` with no extra plumbing. Always `None` for a `Regression` decoder (a continuous target has no discrete label list).

    `Decoder.__call__()` (what `N2O.run()` actually calls, not `decode()` directly) auto-detects a raw, unwindowed recording (`hasattr(signal, "datasets") and hasattr(signal.datasets[0], "raw")` — what `DatasetLoader.read()` returns) and calls `prepare()` on it *once*, caching the result in `self._prepared_windows` — a raw recording is a bounded offline dataset in this project (see `signal/dataset/` above), so nothing legitimately changes it between calls; re-preparing every call would just redo the same expensive filter/window work for the same result. `self.cycle` (default `1`, set in `Decoder.__init__()`) decides which prepared window `__call__()` picks: `cycle <= 1` always decodes the *most recent* window (mirrors a live stream, where only the newest chunk matters); `cycle > 1` picks one of `cycle` windows spread evenly across the prepared set, advancing (and wrapping around) on every call. `N2O.run()` reads `getattr(self.decoder, "cycle", 1)` to decide how many steps to loop — see below — so a decoder meant to demo several different results per `N2O.run()` cycle off a static recording (e.g. `OfnerEEGNet`, `self.cycle = 3`) raises it in its own `__init__()`; an ordinary decoder leaves it at `1`.

    `classification/`, `regression/`, and `utils/` are real subpackages under `decoder/`, each following the project's usual "`base.py` ABC + one file per concrete implementation" shape: `classification/base.py` and `regression/base.py` hold `Classification(Decoder)`/`Regression(Decoder)` — the two task-type ABCs every concrete decoder actually subclasses (not `Decoder` directly): both implement `preprocess()` with `bandpass_standardize()` (4-38Hz bandpass + exponential-moving-standardize — filtering/normalizing doesn't depend on task type), but `window()` differs by what the target looks like — `Classification.window()` is `window_by_event()` (one event-locked window per trial, for a single per-trial label, and where `config.labels` gets set); `Regression.window()` is `window_by_sliding()` (overlapping fixed-length windows tiled across the whole recording, ignoring trial/event boundaries entirely, since a continuous target like a joint angle doesn't have one value per discrete trial).

    `classification/braindecode_entry.py` mirrors `signal/dataset/moabb_entry.py`'s approach for `braindecode.models`: `BRAINDECODE_MODEL_REGISTRY`/`list_models()` are populated at import time from every `braindecode.models.EEGModuleMixin` subclass (~60 architectures), and `BraindecodeDecoder(Classification)` (`name, *, n_chans, n_outputs, n_times, **kwargs`) builds any of them by name instead of hand-writing a subclass per architecture. Unlike a moabb dataset class, a model isn't zero-arg constructible — its layers are shaped by `n_chans`/`n_outputs`/`n_times`, so those stay required constructor arguments (no dataset-agnostic default). `BraindecodeDecoder.decode()` runs a real forward pass and returns the predicted class index; `.model` is the raw `torch.nn.Module` for loading pretrained weights onto (see `examples/03_explore_eegnet_decoder.ipynb`). Since `BraindecodeDecoder.__init__` needs `n_times` up front to build the model's layers, `utils/windowing.py`'s `expected_window_samples(raw_dataset, start_offset_sec=..., stop_offset_sec=...)` predicts what `window_by_event()` will produce (from the same trial-annotation-duration + sfreq facts `create_windows_from_events` itself uses) without actually windowing first — so a decoder can be built *before* calling `prepare()` on the raw data, rather than windowing manually just to measure the result and only then constructing the model (see `examples/03_explore_eegnet_decoder.ipynb`, both the fresh-`EEGNet` and the pretrained-checkpoint sections).

    `BraindecodeDecoder.from_pretrained(name, repo_id, **kwargs)` supports **only** checkpoints published via braindecode's own Hub-native `model.push_to_hub()` (i.e. `repo_id` has a real `config.json` — checked via `huggingface_hub.HfApi().file_exists(repo_id, "config.json")`, no download). For that kind, shape *and* weights load fully automatically through `BRAINDECODE_MODEL_REGISTRY[name].from_pretrained(repo_id)` (built into `EEGModuleMixin`/`huggingface_hub.PyTorchModelHubMixin` — no n2o-side registry or per-checkpoint code). A checkpoint saved via skorch's own `EEGClassifier.save_params()` instead (e.g. `braindecode/plot_bcic_iv_2a_moabb_trial`, used by `examples/03_explore_eegnet_decoder.ipynb`) has no `config.json` at all (checked directly against the real repo — only `params.safetensors`/`history.json`/`metadata.json`), and its shape isn't recoverable from the raw weight tensors either (a tensor's shape encodes `n_chans`/`n_outputs` at a different position per architecture, and `n_times` is unrecoverable post-pooling/conv with no inverse braindecode exposes — verified by inspecting real tensors from two different architectures, not assumed). `from_pretrained()` raises a clear error for that kind; build the decoder with the plain constructor (explicit `n_chans`/`n_outputs`/`n_times`) instead, same as `examples/03` does.

    `utils/preprocessing.py`/`utils/windowing.py` (moved from `signal/dataset/`) hold the non-model helpers — turning a raw recording into decoder-ready trials is treated as the decoder's responsibility, not the signal source's. `bandpass_standardize()`, `window_by_event()`, and `window_by_sliding()` are the plain functions `Classification`/`Regression` call from their own `preprocess()`/`window()`, but they're also usable directly on whatever `signal.read()` returns, e.g. `bandpass_standardize(dataset); windows = window_by_event(dataset, start_offset_sec=...)`. `window_by_event()`'s `start_offset_sec` has no dataset-agnostic default — it comes from the dataset's own `interval[0]`, the same value `DatasetInfo.data_range_sec[0]` reports. `label_names(windows_dataset)` reads the class-index-ordered label names back off event-locked windows (from `create_windows_from_events`'s own mapping) instead of a caller hardcoding a guessed list. `examples/01_explore_eeg_dataset.ipynb` calls `bandpass_standardize()`/`window_by_event()`/`label_names()` directly, stepwise.
- `command/` — translates a decoder's raw prediction into per-part actions (`Command`, `ActionType`, `CommandConfig`)
- `robot/part.py` — `Part`, the single ABC every concrete actuator/sensor subclasses (replaced the old, removed `RobotArm`/`RobotHand`/`Controller` three-tier split). Declares `goal(cmd)` (pure computation, no I/O — the target values only) and `move(cmd)` (drives the real hardware) as abstractmethods, plus a concrete `done_event` property (`threading.Event`, created lazily on first access): `Robot.router()` clears it right before dispatching this part and sets it right after it finishes (success or failure), so a caller can `part.done_event.wait()`/`.is_set()` to know a part has genuinely finished moving.
- `robot/arm/`, `robot/hand/`, `robot/camera/` — actuators/sensors. `arm/so101/` and `hand/amazing_hand_right/` are each one self-contained subpackage — driver code (`__init__.py`, the `Part` subclass), bundled CAD/sim assets (`mjcf/`, `unity_model/`), and a provenance `NOTICE.md` all live together, since they're facts about the same piece of hardware. `camera/` is still an empty placeholder (`__init__.py` says so).

    `SO101Arm` (`arm/so101/__init__.py`) owns the real SO-101 5-DOF connection directly — `goal(cmd)` is a pure `GESTURES["up"|"down"]` dict lookup, `move(cmd)` lazily connects (first call) then ramps only the `shoulder_pan` joint toward the target in joint-degree space, speed-capped (`MAX_JOINT_SPEED_DEG_S`) so no per-step delta exceeds lerobot's own `max_relative_target` clamp. `arm/so101/lerobot_robot_so101_5dof/` is a verbatim vendored copy of a private local package's 3 files (`SO101Follower5Dof`/`SO101Follower5DofConfig`, a `lerobot`-framework `Robot`/`RobotConfig`, not an `n2o.robot.Part`) — plain source, not a pip/uv dependency, needing `lerobot[feetech]` (`examples`/`demos`-group), lazily imported. `SO101IKSolver`, also inside that vendored folder (an intentional exception — see `robot/solver/` below), is pure Cartesian-offset IK (damped least squares against the bundled MJCF) but isn't wired into `SO101Arm.move()`/`goal()` yet, since no shipped `Command` emits `(ActionType, {"dx", "dy"})` commands yet (see `ROADMAP.md`).

    `AmazingHand` (`hand/amazing_hand_right/__init__.py`) owns the real `rustypot` servo connection directly — `goal(cmd)` is a pure `GESTURES[cmd]` lookup (9 named poses), `move(cmd)` lazily connects (torque-enabling every motor on first call), then sends each motor's gesture value plus its own bundled calibration offset, clamped to a hardcoded safe range (the vendor SDK has none). `disconnect()` torque-disables every motor. Needs `rustypot` (`examples`/`demos`-group), lazily imported. Named `_right` because the bundled CAD/calibration are for the right-hand CAD variant specifically (see `NOTICE.md`) — a left-hand variant would be a sibling package, not a flag on this one.
- `robot/solver/` — `base.py` holds only the shared `Solver` ABC (`solve()`, pure computation, no hardware/sim I/O). Concrete part-specific solvers (e.g. `SO101IKSolver` above) live inside that part's own folder, not here — see `ROADMAP.md`/`robot/메모.md`.
- `robot/vla/` — empty placeholder for `ControllerType.VLA` routing, not implemented yet (`Robot.router()` raises `NotImplementedError` for it currently).
- `robot/simulation/` — visualizes a `Part.goal()` target instead of driving real hardware; `mujoco` is a core `n2o` dependency (see below, pinned to the 3.12 line specifically to match the native library vendored for the Unity plugin), but nothing under `n2o`/`n2o.robot` imports `robot/simulation/` eagerly regardless — only `import n2o.robot.simulation` itself, or `N2O.run(controller="simulation")`, requires it at runtime. `mujoco/simulator.py`'s `Simulator` is the default backend: one shared `_MujocoModel` (one MJCF spec/window, merging `arm/so101/mjcf/` + `hand/amazing_hand_right/mjcf/` into a single spec via `mujoco.MjSpec.attach()` when both parts are passed, optionally welding the hand onto the arm's gripper site via `attach_hand_to_arm=True`) across every part passed to `parts=`. `drive(part, target)` converts that part's own `goal()`-shaped target into actuator ctrl values and steps physics (thread-safe via an internal lock, since `Robot.router()` dispatches arm/hand concurrently); `launch_viewer()` opens a live GLFW window and registers it with `mujoco/viewer.py`'s `enable_live_view()`/`wait_for_viewers()` (an `atexit` hook that blocks process exit until every live viewer window is closed); `render()` returns a headless-safe offscreen RGB frame. `unity/unity_simulator.py`'s `UnitySimulator` is an alternate backend with the same `parts`/`attach_hand_to_arm`/`drive()`/`launch_viewer()`/`close()` shape, talking to a companion Unity process over a TCP JSON handshake instead (see `UnitySimulator`'s own docstring for the wire protocol — this repo doesn't ship the Unity-side project itself, only its 3D model as a local package, see `robot/arm/so101/unity_model/`/`robot/hand/amazing_hand_right/unity_model/`) — assign one to `robot.simulator` manually before calling `run()`/`prepare()` to use it, since `N2O.prepare()` only auto-builds the MuJoCo one. `UnitySimulator`'s own wire protocol doesn't care which of two engines is actually listening on the Unity side: `unity/solver/closed_loop_rig.py`'s `ClosedLoopRigSolver(Solver)` reads a part's MJCF via `mujoco` (lazy-imported, same rule as `unity/utils/mjcf_reader.py`'s plain reader functions it builds on) and emits a JSON rig descriptor for a from-scratch `ArticulationBody` rig (AmazingHand's ball-joint/`<equality><connect>` mechanism, which `ArticulationBody` can't express natively, is bridged with a `ConfigurableJoint` per Unity's own documented technique for kinematic loops — see `DECISIONS.md`'s 2026-09-04 entry); the official MuJoCo Unity plugin is the other engine, loading either MJCF directly with no conversion at all. Neither engine's C# side lives in this repo at all — see the companion `neural-to-output-unity` repo (not yet published) for the actual Unity project and scripts (`RigLoader.cs`/`MujocoPluginBridge.cs`/etc.), a separate deployable repo rather than something bundled here (this repo ships only the Python side that produces the JSON rig descriptor the Unity side consumes).

`ClosedLoopRigSolver.__init__`'s optional `attach=(attach_mjcf_path, site_name, prefix)` merges a second part's MJCF onto the first's own named site before extracting the rig — mirrors `Simulator`'s own `attach_hand_to_arm=True` merge exactly (`mujoco.MjSpec.attach()`, the same `ARM_GRIPPER_SITE`/`HAND_PREFIX` constants, now promoted to public names on `mujoco/simulator.py` so both call sites import the one shared source of truth instead of each hardcoding the site name) — so a Unity-native (`ArticulationBody`) rig can weld a hand onto an arm's gripper site the same way the MuJoCo backend already does, in one combined rig.json instead of two separate ones. Welding is a plain rigid parent-child attachment, not a kinematic loop, so `RigLoader.cs` needs no changes to render it — it already builds its tree generically off each body's own `"parent"`. The resulting rig's `"attached_mjcf"` key (alongside the always-present `"source_mjcf"`) is what `rig_json_status(rig_json_path, mjcf_path, attached_mjcf_path=None)` (same module) reads back to report `"missing"`/`"stale"`/`"current"` for a given rig.json against the MJCF(s) it's supposed to match — used by `apps/console.py`'s part settings dialog to show a non-blocking status label next to the "rig.json 재생성" button (never gates which engines are offered — that would be a chicken-and-egg UX, needing a rig.json to unlock the button that creates one).

`robot.Robot` is a plain container binding one `arm` + `hand` + `camera`, plus `controller` (a `ControllerType`: `SIMULATION`/`MOTOR_DRIVER`/`VLA`, default `SIMULATION`) and `simulator` (`None` by default). `Robot.router(actions)` dispatches every part named in `actions` (`"arm"`/`"hand"`, not `camera`) on its own thread — a real concurrency win despite the GIL, since both `Part.move()` (serial I/O + `time.sleep()` ramping) and `Simulator.drive()` (`mujoco.mj_step()`) release it while blocked. Per part, depending on `self.controller`: `SIMULATION` calls `obj.goal(cmd)` then, if `self.simulator` is set, `self.simulator.drive(part, target)`; `MOTOR_DRIVER` calls `obj.move(cmd)`; `VLA` raises `NotImplementedError` (see `robot/vla/` above). A part is skipped entirely (no thread spawned) when `actions.get(part)` is `None` or `getattr(self, part)` is `None` — "nothing to do this step" (e.g. `OfnerCommand`, which only ever targets one part per call) is handled the same way as "this part doesn't exist". If more than one part's thread raises, only the first (`arm` before `hand`) is re-raised.

`N2O` (`n2o/__init__.py`) wires a `signal` + `decoder` + `command` + `robot` together (no separate `controller` attribute — see `FeatureType.LANGUAGE` below). A `Decoder` instance is callable (`self.decoder(sample)` is shorthand for `.decode(sample)`) — except `__call__()` first checks whether `sample` is still a raw, unwindowed recording (`hasattr(sample, "datasets") and hasattr(sample.datasets[0], "raw")`, the same shape `DatasetLoader.read()`/`StreamLoader.read()` return), and if so `prepare()`s it (cached, `cycle`-aware — see the `decoder/` bullet above) before decoding. An already-windowed array (the common case in a real per-step `signal.read()`) skips this and goes straight to `decode()` unchanged. Every `Decoder` subclass must declare an `output_type` ClassVar (`FeatureType.ACTION` or `FeatureType.LANGUAGE` — there is no other valid value, and `run()` raises `ValueError` if it's unset or anything else).

`N2O.prepare(controller: str = "motor_driver")` writes `ControllerType(controller)` onto `self.robot.controller`, and — only for `"simulation"`, and only if `self.robot.simulator` isn't already assigned (a caller that pre-assigned e.g. a `UnitySimulator` is left alone) — lazily builds a `Simulator` covering whichever of `arm`/`hand` are actually assigned and calls `launch_viewer()` on it. `N2O.run(controller: str = "motor_driver")` calls `prepare(controller)` then loops `_run_cycle(i, cycle)` `cycle = getattr(self.decoder, "cycle", 1)` times (see the `decoder/` bullet above for what sets `cycle`), catching `KeyboardInterrupt` to exit cleanly. There's no settle-sleep between cycles anymore — `Robot.router()` already blocks on every dispatched part's `Part.done_event`, which isn't set until `move()`/`Simulator.drive()` has genuinely finished (real or simulated), so cycles are naturally paced by real completion time. `_run_cycle()` prints per-cycle progress (`[i/cycle] 추론 진행 중`, ticking a `.` once a second via a background-thread read+decode, then `추론 결과: <label>` once done, resolving through `decoder.config.labels` when set instead of printing a bare class index), then dispatches: `FeatureType.LANGUAGE` currently just `raise NotImplementedError` (no controller/language-routing design exists yet — despite what `docs/controller/index.md` still describes, which needs its own sync pass); `FeatureType.ACTION` calls `command.translate(decoder, decoded_signal)` then `robot.router(actions)`; anything else raises `ValueError`.

`DatasetLoader`'s `name=` is backed by a registry, `DATASET_LIBRARY` (populated by `@register_dataset("Name")` on a `DatasetLibraryEntry` subclass) — its values are never instantiated directly by the caller; `DatasetLoader(name="...")` stays the sole entry point and `DatasetLoader.read()` delegates to the matching entry internally. This keeps `DatasetLoader` a thin dispatcher instead of special-casing every named dataset's file format inline. `robot.arm`/`robot.hand`/`robot.camera` have no equivalent name-based registry — assign a `Part` instance directly (`robot.arm = SO101Arm(...)`).

`Command` (in `n2o/command/command.py`) is a plain overridable class, not a declarative config — its default `translate()` assumes `decoded_signal` is already keyed by robot part (`{"arm": ..., "hand": ...}`); subclass and override `translate(self, decoder, decoded_signal)` whenever a decoder's raw output needs real translation into that shape first. Each part's resulting value is either a bare, already self-describing name (e.g. `"grip"`) or an `(ActionType, value)` tuple for raw values that aren't self-describing on their own (e.g. a regression number/dict) — `ActionType` (`JOINT_ABSOLUTE`, `JOINT_RELATIVE`, `CARTESIAN_ABSOLUTE`, `CARTESIAN_RELATIVE`) travels with the value, independent of the decoder's own `DecoderType`. Keep a `Decoder` a plain predictor (raw prediction out) and put the prediction → per-part-action mapping in `Command`, not in the decoder — that's the whole reason `Command` exists.

A `Command` subclass is usually notebook-local rather than a shipped `n2o.command` class, since it encodes one specific decoder's raw output → one specific robot's parts. Two exceptions are shipped in `src/`: `GripSpreadCommand` (`n2o/command/grip_spread.py`) maps `BNCI2014_001`'s four raw motor-imagery labels (`feet`/`left_hand`/`right_hand`/`tongue`) to `AmazingHand`'s four single-finger poses, reusable by any decoder that predicts that same label set (see `examples/04_hand_intent_classification_amazinghand.ipynb`); `OfnerCommand` (`n2o/command/ofner_command.py`) maps `OfnerEEGNet`'s seven raw labels to one arm-or-hand gesture each via `LABEL_TO_GESTURE` (`decoder.config.labels[decoded_signal]` resolves the raw class index back to its label string first) — used by `demos/quickstart.py`. Its current mapping is a placeholder (arbitrary `"up"`/`"down"`/`"grip"`/`"release"` assignment, chosen only so it round-trips through `SO101Arm.GESTURES`/`AmazingHand.GESTURES` without a `KeyError`), not a considered design — expect it to change.

`CommandConfig` (in `n2o/command/config.py`) is a separate, declarative contract for the `command` boundary — pairs with `Command` the same way `signal`/`decoder` pair `SignalConfig`/`DecoderConfig` with their runtime classes. There is no `N2O.verify()` method; call `n2o.command_config.verify_report(n2o)` directly (`n2o.command_config` is a plain attribute, set by the caller) to walk `signal -> decoder -> command -> robot.arm/hand` and print a match/mismatch/미정 table. `DecoderConfig.type` can be a `tuple[DecoderType, ...]` for a decoder wrapping more than one internal model (e.g. one classifier + one regressor with no shared trunk); `Command.translate()` reads `decoder.config.type` (an instance attribute, set in `__init__`, not a ClassVar) to decide how to interpret `decoded_signal`.

The old `RobotArm`/`RobotHand`/`Controller`/`MotorWrapper` split (a separate per-part dispatcher object a robot-arm/hand implementation owned and delegated `move()` to) is gone — `SO101Arm`/`AmazingHand` each own their real hardware connection directly inside `move()`/`_ensure_connected()`/`_ensure_servo()` (see the `robot/arm/`/`robot/hand/` bullet above). Write a new `Part` subclass directly for hardware this project doesn't already ship a driver for, rather than a separate controller-style helper object.

To add a new stream/robot part: subclass the relevant `base.py` ABC in a new file next to the existing ones in that package, then re-export it from that package's `__init__.py`. To add a new decoder, subclass `Classification` or `Regression` — whichever matches the decoder's `output_type`/`DecoderType` — not `Decoder` directly, unless its `preprocess()`/`window()` genuinely needs a third shape neither one provides. A new *moabb* dataset library needs no code — it's already registered under its class name in `moabb.datasets.utils.dataset_list` (check `DatasetLoader.list_libraries()`/`library_tree()`). To add a dataset moabb doesn't cover, register a hand-written `DatasetLibraryEntry` subclass in a new file under `signal/dataset/` with `@register_dataset("Name")`, then re-export it from `signal/dataset/__init__.py` — or, if it's a local recording rather than a redistributable public dataset, use `n2o.signal.dataset.write_metadata_template(path)` + `DatasetLoader(path=...)` instead of the registry entirely.

`tests/` mirrors `src/n2o/`'s package layout: a test for one module's own behavior (e.g. `Command.translate()`) lives in the matching subfolder (`tests/command/test_command.py`, next to `src/n2o/command/command.py`); a test that exercises how modules connect (e.g. `N2O.run()` routing across `signal`/`decoder`/`command`/`robot`) lives directly under `tests/` (e.g. `tests/test_run.py`), not in any module subfolder.

`examples/` holds numbered, self-contained Jupyter notebooks (e.g. `examples/01_explore_eeg_dataset.ipynb`) — each notebook interleaves the explanation (markdown cells) with the runnable code, meant to be worked through in order, and is this project's tutorial content (see [examples/README.md](examples/README.md)). Usage documentation that isn't tied to a runnable notebook — how the pipeline's pieces fit together, how to extend them — lives in `docs/` instead (see above), not duplicated here.

`moabb` and `braindecode` are core `n2o` dependencies (not examples-only) because `signal/dataset/moabb_entry.py` needs `moabb.datasets` at import time to populate `DATASET_LIBRARY` — see `signal/dataset/` above. `mujoco` is also core (pinned `>=3.12.0,<3.13.0` — see `robot/simulation/` above; the exact minor version matters because it must match the native `libmujoco.so` the companion `neural-to-output-unity` repo's MuJoCo Unity plugin engine uses) since `n2o.robot.simulation.unity.solver.ClosedLoopRigSolver`'s rig-generation CLI is a real, documented capability of the installable package, not example/demo-only convenience. The `examples` dependency group (`uv sync --group examples`) pulls in the remaining extra packages notebooks use (`jupyter`, `lerobot`, etc.) that aren't needed outside a notebook/robot demo — keep those out of `dependencies` / other groups.

`demos/` holds standalone scripts built on top of `n2o` (e.g. `demos/quickstart.py`), sharing an `examples`-based `demos` dependency group (see [demos/README.md](demos/README.md)). `apps/` is the same idea but for a desktop GUI instead of a script — kept as its own top-level folder (not a `demos/` subfolder) so its UI-only dependency (PySide6) stays in its own `app` dependency group rather than leaking into `demos`' plain-script one. `apps/console.py` wires the same signal/decoder/command/robot components `demos/quickstart.py` does, but through dropdowns instead of hardcoded values, split across two windows (`ConsoleWindow` for configuration, calling `N2O.prepare()`; a `RunPanel` it opens for the actual `N2O.run()` call — see [apps/README.md](apps/README.md)); `apps/console.desktop` launches it from a Linux app menu.
